Major architecture features / subsystems to implement:

    - Memory management. The plan is essentially an architecture split into
      physical and virtual memory management subsystems, where the physical
      memory manager is a buddy allocator + a page allocator backed by the
      buddy allocator, and the virtual memory manager can be the usual thing
      relatively similar to an extent allocator.

      More specifically, we have an array of memory region descriptors,
      and each memory region is an array of page descriptors, the buddy
      allocator allocates by going through regions until it finds one that can
      satisfy the allocation, then doing the normal algorithm on that of
      either grabbing an exact fit, or splitting the larger blocks. As for
      freeing, given a page's physical address we first find the region
      containing it, and after that the expression
            `(PHYS_ADDR - REGION_START) / PAGE_SIZE + REGION_START`
      will give us the address of its metadata, or
            `((PHYS_ADDR XOR BLOCK_SIZE) - REGION_START) / PAGE_SIZE + REGION_START`
      for its buddy.

      Then for virtual memory, we maintain an AVL tree of virtual memory
      regions, a virtual memory region has metadata such as its start, end,
      and type.

      Our vm_mkregion() can create a new region (doesn't need to map any pages
      yet or allocate memory), vm_delregion() can tear one down (must unmap
      all pages). Then on page faults we check "is this page in a virtual
      region?", and if yes, we map it.

      What then is the buddy allocator for if in practice we allocate one page
      at a time? The answer is for acquiring physically contiguous memory
      larger than 4KB. (mainly for device drivers)

      Finally, it doesn't need to support PAE immediately, but we should avoid
      writing anything that depends on PAE not being implemented, this means
      we need to treat addresses as being 8-byte structs, thankfully though
      this doesn't mean we literally need to juggle these large structs in the
      buddy allocator or page frame allocator, those can work with PHYS / 4096,
      or in other words, the page frame number rather than the address.

Critical Issues:

    - Stack frames. Like an absolute idiot, when I was designing my runtime I
      decided on 4 runtime-reserved registers and the other 4 being
      caller-saved. The issue is that without even a single callee-saved
      register it is impossible to save a base pointer without going through
      several layers of indirection and putting it in a global variable.

      There are three ways to deal with this:
            a) Accept it and deal with the fact that everything will be slow
               as shit since all function calls get one practically guaranteed
               cache miss. (no way am I doing that, I designed this to be
               capable of being optimized)

            b) Pick one of those registers to become callee-saved. In theory a
               good idea and what I should have done from the start, but in
               practice I cannot magically take 4000 lines of assembly code
               and make all of it follow an entirely new calling convention.

            c) Use the return stack. In theory it should be easy enough to
               regex my way through the codebase and add a single `push ebp`
               to the start of every function and a `pop %reg` on the
               caller-side. It's not as slow at runtime as option a, not as
               slow to implement as option b, but not as performant as b, and
               will increase code size.

    Honestly, I don't think option b would even be that much more performant.
    In practice 4 live values is the exact amount that a lot of simple
    functions use, I'd lose a lot of performance if I took away that
    register... But maybe there's another option. I present, option d:

        d) A hybrid of b and c, we use a callee-saved register, but make the
           return stack the mechanism by which it is restored. Most likely
           edx, since all functions currently treat eax, ebx, ecx, and edx as
           undefined after a function call, this would not impact existing
           calls at all, we simply add `push edx` at the start of every
           function and `pop edx` at the end. It's only 2 instructions per
           function, and only for functions that modify edx, and it keeps
           words that walk the return stack relatively simple, as they can
           always treat it as a simple 8-byte struct with a frame base value
           and an instruction pointer value. And this also means that while
           edx becomes the frame base for locals for instance, functions that
           *don't* use edx for that still work fine since they can otherwise
           treat it as caller-saved, and new functions for the ABI can use edx
           as an accumulator register if they don't need it for locals, since
           any operations done on it are now retained across calls.
